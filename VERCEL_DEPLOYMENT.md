# Visitor Helper Desk — Vercel deployment candidate

## Deploy a fresh database
1. Extract the ZIP and open the directory containing app.py and vercel.json. Do not copy old .env, local databases, selfies or backups into the repository. Keep those offline.
2. Create a private GitHub repository and push this directory. Import it in Vercel; choose the Flask framework (or automatic detection), root directory containing app.py, and default build settings. Python 3.12 is selected in .python-version.
3. In Vercel Marketplace add Neon PostgreSQL and connect it to the project, or use another PostgreSQL provider with TLS. Set DATABASE_URL to its pooled connection URL (keep it secret). Enable production environment access. Do not connect untrusted preview deployments to production data.
4. In Vercel Settings > Environment Variables add VHD_ENV=production, VHD_ADMIN_PASSWORD (new strong unique password, at least 12 characters), VHD_SECRET_KEY (new random key, at least 32 characters). Generate the latter locally using python -c "import secrets; print(secrets.token_hex(32))". Do not reuse any prior exposed credentials. Enable automatic exposure of system environment variables; VERCEL_URL and VERCEL_PROJECT_PRODUCTION_URL are accepted automatically. Add custom domain hostnames, comma separated, to VHD_ALLOWED_HOSTS if needed. No https:// or path in that value.
5. Deploy/redeploy. The app initializes the PostgreSQL schema on first start. Open /health, then / and /admin/login. Test with dummy data before real visitors. Check that a selfie remains accessible after redeployment. Verify Windows webcam and mobile camera over HTTPS, admin logout, unauthorized selfie access, delete, CSV export and rate limit. Confirm function logs show no errors.
6. Audit the new dependencies in a clean Python 3.12 virtual environment: python -m pip install -r requirements.txt; python -m pip install pip-audit; python -m pip_audit; python -m unittest discover -s tests -v. Tests use local SQLite and do not verify the cloud path. Run live tests against an authorized staging deployment before collecting PII.

## Important architecture changes
- PostgreSQL stores compressed JPEG selfies as BYTEA in the same transaction as visitor data; there is no public selfie URL or filesystem persistence requirement. Delete removes the database row and its photo in cloud mode. Database-backed per-IP rate limits use transaction advisory locks. Provider database backups include photos. Separate Blob/Redis services are not needed for this small installation.
- Static assets including the original large brochure are under public/static so Vercel can serve them outside function payload limits. Registration uploads limited to 3 MiB with client-side compression and server-side re-encoding; request limit 4 MiB. Large CSV exports may exceed Vercel's response limit; use narrower filters or provider export. Cloud backups/restores are through PostgreSQL provider or pg_dump/pg_restore; SQLite backup/restore UI is hidden on cloud. Retention cleanup is best effort on cold start, not a scheduled job. No OTP verification or face liveness verification is implemented.
- Fresh cloud database starts empty. Existing records and local selfies are NOT automatically imported. Preserve offline backups; arrange a controlled migration if needed. Do not upload personal data to GitHub. Confirm provider data retention, backups, permissions, region, cost and Vercel plan eligibility for commercial use before public rollout.
- This is a code conversion, not a verified live deployment. Local Python syntax, JS syntax and ZIP integrity were checked; cloud PostgreSQL integration, new dependency audit and live security tests require the target environment. Prior test results do not cover this version.
